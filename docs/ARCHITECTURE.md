# Architecture

## Stack

Expo SDK 57 / React Native 0.86 (New Architecture only), TypeScript, Expo Router (file-based routes in `src/app`), `expo-audio` for playback, `expo-image` for cached artwork, AsyncStorage for settings/caches, `expo-secure-store` for credentials. Built locally with Gradle (no EAS); `android/` is generated by `expo prebuild`.

```
src/
  app/            routes — (tabs)/{index,library,search,settings}, album/[id], artist/[id], playlist/[id], now-playing, login
  components/     Cover, SongRow, AlbumTile, EntityMenu, MiniPlayer, StatsOverlay, RadioProgress, ui
  lib/
    subsonic.ts   API client + media URLs
    player.ts     queue / engine / persistence / scrobbling
    radio.ts      the radio algorithm       radios.ts  saved radios       radioUi.ts  start-radio flow state
    settings.ts   persisted settings        theme.ts   palettes           cache.ts    SWR JSON cache
    menu.ts       global actions-sheet state   format.ts  display helpers
modules/traffic-stats/   local Expo module (Kotlin): Android TrafficStats rx bytes
```

State is deliberately simple: small module-level stores exposed through `useSyncExternalStore` (`player`, `settings`, `radios`, `menu`, `radioUi`) — no state library.

## Subsonic client (`lib/subsonic.ts`)

- **Auth:** token auth (`t = md5(password + salt)`). One salt per session, so media URLs are **stable** within a session (needed for image caching; the artwork `cacheKey` keeps the disk cache valid across sessions even though the salt changes).
- **Endpoints used:** `getArtists/getArtist/getAlbum/getAlbumList2/getRandomSongs/search3/getStarred2`, `getArtistInfo2` (similar artists), `getSimilarSongs2`, `getTopSongs`, `star/unstar`, `scrobble`, playlist CRUD, `getCoverArt`, `stream`.
- **Quality:** `stream` gets `format`/`maxBitRate` when a transcoded quality is selected; original = untouched file.
- JSON API traffic is counted in `net.apiBytes` for the stats overlay.

## Player (`lib/player.ts`)

One long-lived native `expo-audio` player + a **JS-side queue**. `expo-audio`'s lock-screen integration is per-player (no native next/previous, no native queue), so advancing on `didJustFinish` is done in JS.

- `base` = queue in original order, `queue` = actual play order. Shuffle keeps the current track first and shuffles the rest; turning it off restores `base` and finds the current track again.
- Repeat `off | all | one`; play next / add / remove / jump; `playSongs(songs, start, {shuffle?, radio?})`.
- **Scrobbling:** "now playing" on load, "played" at min(50 %, 4 min). This is what feeds *Recently played* / *Most played* on the server.
- **Persistence:** queue/index/shuffle/repeat saved (debounced) and restored paused on launch; last 200 played ids kept for radio de-duplication.
- **Radio hook:** when a radio is active and ≤ 6 tracks remain, `radio.more()` appends more.

## Radio

Why not genre: the library's genre tags are inconsistent, so genre is a weak tiebreak only. Instead, radio walks the **related-artist graph** Navidrome exposes (`getArtistInfo2.similarArtist`, already restricted to artists present in the library).

`buildRadio(seed)` (`lib/radio.ts`), seed = song | artist | album | *mix* (artists you actually play):

1. **Seed artists.** Song/artist: their artist. Album: the album artist, or — for compilations / "Various Artists" / unknown — the real artists of the tracks. Mix: artists from *frequent* and *recent* albums.
2. **Graph crawl, 3 hops, beam of 14.** Each hop expands the best unexpanded nodes (6 requests in parallel). A neighbour's score gains `parent.score × 0.6 × (1 − rank/(n+4))`, **accumulated over every path**, so an artist reachable from several neighbours outranks a one-off.
3. **Song-level similarity** (`getSimilarSongs2` on the seed's tracks) runs alongside and also nudges artist scores — it bridges artists the graph can't reach.
4. **Gather tracks** from the top ~28 artists (`getTopSongs`, falling back to a few random albums when that's empty). Candidate weight = `artistScore^0.8 × (0.6–1.0 random)`, +starred, +tiny genre bonus, ×0.3 if played recently.
5. **Sequence** by weighted sampling with an **artist cooldown** (no repeat within 3) and a **cap of 4 tracks per artist**; a song seed plays first.
6. **Thin pool?** (< 30 candidates: sparse graph or junk seed) top up with genre/random tracks at low weight, so a radio is never a one-track dead end.
7. **Extend lazily:** `session.more(n)` pulls the next-best unfetched artists, crawls one more hop, or tops up — same machinery, no restart.

Every radio is saved (`radios.ts`: seed + snapshot of the first 40 tracks). Replay is instant from the snapshot; the crawl only runs when the queue needs extending (`resumeRadio`). Typical build: 15–45 s (first-time lookups on the server are slower than cached ones) with a cancellable progress dialog.

## UI structure

- Custom bottom tab bar renders the mini player above the tabs; stack screens render the mini player themselves; Now Playing is a modal.
- One global **EntityMenu** sheet (songs/albums/artists) driven by `lib/menu.ts`; it remounts per item (keyed) so per-item state resets without effects.
- Lists are virtualised (`FlatList`); library lists are cached (stale-while-revalidate) in `cache.ts`; artwork via `expo-image` with `cachePolicy="disk"`.
- Themes (`lib/theme.ts`): every palette has `accent` (primary), `accent2` (active track / progress) and `accent3` (radio / live stats).

## Stats overlay & `traffic-stats`

JS `fetch` can't see native audio streaming, so a ~10-line Kotlin Expo module returns `TrafficStats.getUidRxBytes(myUid)`. The overlay samples it each second: session total and per-track delta are **real bytes on the wire** (audio + artwork + API), not estimates.

## Decisions

- **Expo/React Native over native Kotlin or Rust.** The workload is network + native decode (Media3 inside `expo-audio`) + list rendering; Hermes handles the small amount of JS logic. A Rust core would add a bridge and cross-compile step for no user-visible win. If native feel ever matters, the next step up is Kotlin/Compose, not Rust.
- **`expo-audio`, not `react-native-track-player`:** RNTP doesn't support the New Architecture, which RN 0.86 requires.
- **JS queue, not a native playlist:** `expo-audio`'s playlist lacks lock-screen metadata/controls; the per-player lock-screen API is used instead.
- **Cleartext HTTP allowed** (`usesCleartextTraffic`): intended for Tailscale addresses, where WireGuard provides the encryption.

## Limitations & roadmap

- Lock-screen/notification has no next/previous (expo-audio limitation).
- Small gap between tracks (no gapless; would need native queueing / preloading).
- No offline downloads; saved radios are device-local.
- Ideas: full-screen queue drag-reorder, per-radio rename, hot-reload dev client + scrcpy workflow, ReplayGain, Android Auto.
